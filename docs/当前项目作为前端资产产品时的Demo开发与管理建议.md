# 当前项目作为前端资产产品时的 Demo 开发与管理建议

## 结论

当前项目更像一个“带版本演进能力的前端资产产品”，而不只是一个普通代码仓库。

更准确地说，它同时具备三层属性：

- 它是资产库：`packages/*` 在沉淀 UI、页面物料、hooks、services、tokens、store 等可复用能力
- 它是产品：根 [README.md](/Users/sunny/work2026/fe-base/README.md) 明确将项目定位为“前端能力底座”
- 它是版本化平台：`apps/web`、`apps/desktop`、`apps/mobile` 是这些能力的运行壳和承载面

因此，这个仓库的工作重点不是单次功能交付，而是：

- 能力沉淀
- 能力组合
- 多端承载
- 持续迭代和版本演进

---

## 一、如果当前仓库是 product，应如何理解其内部结构

从 product 视角看，当前仓库可以理解为四类资产协同：

- `packages/*`：产品的能力 SKU
- `apps/*`：产品的运行壳和体验壳
- `packages/pages/*`：产品的场景样板间和展示面
- `docs/*`：产品的设计、计划、结论和协作记忆

在这个前提下，`Demo` 不应该再被理解为“随便做一个示例页面”，而应该被理解为：

> 产品研发阶段用于验证高不确定性能力的实验层。

它不属于最终产品形态，但会影响产品能力是否进入正式版本。

---

## 二、如果当前仓库是 product，Demo 应该怎么定位

对于当前项目，Demo 的职责应该是：

- 验证新能力是否成立
- 验证能力边界，而不是展示完整业务场景
- 在进入 `packages/*` 之前消化高不确定性
- 为后续版本提供可复用的决策记忆

换句话说：

- `packages/*` 负责发布能力
- `demo/*` 负责验证能力
- `packages/pages/*` 和 `apps/*` 负责展示和组合能力

这三者不能混为一体。

---

## 三、结合当前架构，最适合的 Demo 开发方式

不建议把 Demo 做成完全脱离当前 monorepo 的独立小仓库。

原因是当前项目的很多能力验证都依赖真实的工程环境，例如：

- 共享依赖
- 真实组件体系
- 类型边界
- 打包链路
- 多端差异
- 路由和样式承载

因此，更适合当前项目的方式是：

> 采用“仓内隔离式 Demo”模式。

即：

1. 在仓库根目录建立 `demo/`
2. 每个 Demo 聚焦一个能力点
3. Demo 可以依赖仓内公共包，但不应直接等同于正式资产
4. Demo 验证通过后，再将稳定能力提炼到 `packages/*`
5. 最后由 `packages/pages/*` 或 `apps/*` 做集成展示和场景承载

建议目录：

```text
demo/
├── README.md
├── demo-drag-canvas/
│   ├── context/
│   ├── src/
│   └── README.md
├── demo-json-form-schema/
│   ├── context/
│   ├── src/
│   └── README.md
└── demo-multi-platform-token-bridge/
    ├── context/
    ├── src/
    └── README.md
```

## 四、针对当前前端架构，哪些事情适合先做 Demo

特别适合先做 Demo 的能力通常有这些：

- 新交互机制：拖拽、画布、布局编排、复杂键盘交互
- 新渲染机制：配置驱动渲染、Schema 渲染、动态组件注册
- 新跨端机制：Web/Desktop/Mobile 复用策略
- 新三方库接入：布局库、编辑器、图表库、复杂表格库
- 性能策略：虚拟化、懒加载、状态拆分是否真的有效
- 设计系统桥接：设计令牌如何映射到多端

这些事项的共同特点是：

- 团队不一定做过
- 做完后结果未必可预期
- 单靠读文档和逻辑推演无法完全确认
- 一旦直接进入正式工程，返工成本偏高

---

## 五、哪些事情通常不需要单独做 Demo

以下类型通常更适合直接在正式工程中实现：

- 常规页面开发
- 已有组件的小扩展
- 样式微调
- 已验证模式下的字段增加
- 明确可预期的 hooks / service / store 改动
- 常规接口封装和数据流接线

判断标准不是“会不会写代码”，而是：

> 做完后结果是否足够可预期。

如果结果高度可预期，没必要额外绕一层 Demo。

---

## 六、如果当前仓库是 product，Demo 应该怎么管理

管理 Demo 的关键不只是“目录怎么放”，而是：

- 生命周期怎么定义
- 什么时候允许开 Demo
- 什么时候允许退出 Demo 进入正式资产
- Demo 和 packages/apps/docs 的边界怎么协作

### 1. Demo 生命周期

建议统一三种状态：

- `active`：当前有效，可继续参考和复用
- `superseded`：已被新 Demo 替代，保留供历史参考
- `archived`：历史归档，不再作为当前决策依据

### 2. Demo 准入条件

只有满足以下条件之一，才建议创建 Demo：

- 团队没做过
- 结果不可预期
- 外部依赖不可控
- 多模块集成风险高
- 多端策略未验证

### 3. Demo 退出条件

一个 Demo 只有满足以下条件，才建议沉淀到正式资产：

- 可以独立运行或独立观察
- 有明确的验证结果
- 有边界说明
- 有集成说明
- 能提炼为稳定能力，而不是一次性试验代码

### 4. Demo 文档要求

每个 Demo 的 README 至少应包含：

- 解决的问题
- 为什么要做这个 Demo
- 验证方式
- 验证结果
- 已知限制
- 推荐沉淀到哪个 package
- 不建议怎么用

### 5. Demo 和版本的关系

如果仓库是 product，那么真正带版本的是 product 本身，而不是每个 Demo。

建议关系是：

- Demo 验证新能力
- Package 沉淀稳定能力
- App / Page 验证集成效果
- Release / Tag 对外形成产品版本

因此，Demo 是版本演进的输入，不是版本主体。

---

## 七、最适合当前仓库的管理模型

结合当前 monorepo 架构，推荐采用“四层模型”：

- `docs/superpowers/specs`：定义想法和方案
- `demo/*`：验证高不确定性能力
- `packages/*`：沉淀稳定共享资产
- `apps/* + packages/pages/*`：组合成产品体验和展示面

这个模型的优点是：

- 不破坏现有 monorepo 结构
- 不否定已有 specs/plans 工作流
- 能补上 Demo 驱动方法论最关键的“隔离验证”环节
- 能让正式资产和实验资产职责更清楚

---

## 八、结论

当前项目确实更像一个有版本演进能力的前端资产产品。

既然它是 product，那么 Demo 就不应该继续混在“页面示例”或“直接进 package”的路径里，而应该被视为：

> 产品研发流程中的独立实验层。

合理的路径应当是：

1. 先用 Demo 验证能力
2. 再把稳定能力沉淀为正式资产
3. 再通过页面和应用组合成产品能力
4. 最终随产品版本一起演进

一句话总结：

> 对当前仓库而言，Demo 最合适的角色不是“示例页”，而是“能力进入正式资产前的验证层”。

# Demo 管理规范 v1

## 目的

本规范用于约束当前仓库中 Demo 的创建、组织、验证、沉淀和归档方式。

目标不是把所有工作都 Demo 化，而是为高不确定性能力建立统一的实验层，使仓库形成稳定协作关系：

- `docs/*` 定义和记录
- `demo/*` 隔离验证
- `packages/*` 沉淀正式能力
- `apps/*` 与 `packages/pages/*` 负责组合和展示

适用范围：

- 当前 `fe-base` monorepo
- Web / Desktop / Mobile 相关能力验证
- 共享包层的高不确定性能力探索

---

## 一、核心原则

### 1. Demo 只服务于不确定性

只有当某项能力存在明显不确定性时，才创建 Demo。  
确定性的工程改动应直接在正式工程中完成。

### 2. Demo 是能力验证单元，不是产品功能页面

Demo 的目标是验证单一能力或关键边界，不是完成一个完整业务页面。

### 3. Demo 是正式资产的前置层

Demo 不是最终交付形态。验证通过后，应将稳定成果沉淀到 `packages/*` 或必要的正式代码中。

### 4. Demo 必须可回溯

每个 Demo 都必须有 README，说明验证了什么、结果如何、限制是什么、后续如何沉淀。

---

## 二、目录规范

仓库根目录统一使用：

```text
demo/
├── README.md
├── demo-{capability-a}/
│   ├── context/
│   ├── src/ 或 doc/
│   └── README.md
├── demo-{capability-b}/
│   ├── context/
│   ├── src/ 或 doc/
│   └── README.md
```

### 目录含义

- `demo/README.md`
  - 说明 demo 根目录用途、命名规则、状态定义、索引方式
- `demo/demo-{name}/context/`
  - 输入材料，如需求摘要、参考资料、约束条件、已有方案
- `demo/demo-{name}/src/`
  - 可运行代码型 Demo 的实现
- `demo/demo-{name}/doc/`
  - 非代码型或方案型 Demo 的验证记录
- `demo/demo-{name}/README.md`
  - 该 Demo 的结论文档

### 目录约束

- 一个 Demo 目录只验证一个明确能力
- Demo 目录不要直接承载正式业务代码
- Demo 可以依赖仓内 package，但不应把自己当成正式 package
- 一个 Demo 不能隐式依赖另一个 Demo 的内部实现

---

## 三、命名规范

Demo 统一使用：

```text
demo-{能力关键词}
```

使用要求：

- 使用 kebab-case
- 名称表达能力，不表达业务页面名
- 名称尽量让人一眼看出其验证目的

### 正例

- `demo-drag-canvas`
- `demo-layout-history`
- `demo-json-form-schema-boundary`
- `demo-token-cross-platform-bridge`

### 反例

- `demo1`
- `demo-feature-page`
- `demo-web-home`
- `demo-new-ui`

---

## 四、状态规范

每个 Demo 只能处于以下三种状态之一：

### 1. `active`

含义：

- 当前有效
- 结论可被后续工作参考
- 可以继续演进或复用

说明方式：

- README 无需额外标注，默认即 `active`

### 2. `superseded`

含义：

- 已被新的 Demo 替代
- 保留用于历史决策追溯
- 当前不应作为首选参考

说明方式：

在 README 开头标注：

```md
> ⚠️ 本 Demo 已被 `demo-xxx` 取代
```

### 3. `archived`

含义：

- 已归档
- 仅保留为历史记录
- 不再作为当前能力判断依据

说明方式：

在 README 开头标注：

```md
> 📦 本 Demo 已归档，仅供历史参考
```

## 五、准入标准

满足以下任一条件，建议创建 Demo：

### 1. 团队没做过

例如：

- 新拖拽引擎
- 新图表引擎
- 新跨端桥接方式

### 2. 结果不可预期

例如：

- 新的渲染策略是否稳定
- 新性能方案是否真的有效
- 动态组件注册模型是否可扩展

### 3. 外部依赖不可控

例如：

- 新三方库实际行为和文档是否一致
- Web / Desktop / Mobile 端行为是否一致

### 4. 集成风险高

例如：

- 一个能力会同时影响组件、页面、状态和多端承载
- 局部可行但整体交互路径未验证

### 5. 边界未验证

例如：

- Schema 驱动组件的边界条件
- 布局历史栈在复杂操作下是否稳定

---

## 六、不建议创建 Demo 的情况

以下场景通常直接在正式工程中实现：

- 常规组件扩展
- 样式微调
- 常规 CRUD
- 已有模式下的字段增加
- 已验证能力范围内的 hooks / services / store 改动
- 明确可预期的路由和页面接线

判断标准统一为：

> 做完后结果是否高度可预期。

如果答案是“是”，则直接做，不额外建 Demo。

---

## 七、退出标准

一个 Demo 满足以下条件后，才能被认为“验证完成”，并进入正式资产沉淀阶段：

### 1. 有明确的验证方式

例如：

- 可运行页面
- 可复现交互
- 可执行测试
- 可对照的性能数据

### 2. 有明确的验证结果

README 中必须写清：

- 成功或失败
- 结论依据
- 关键观察结果

### 3. 已知限制清晰

必须明确：

- 适用场景
- 不适用场景
- 还未解决的问题

### 4. 可抽取为稳定能力

验证通过的内容应能被归入某个正式层：

- `packages/ui`
- `packages/hooks`
- `packages/pages`
- `packages/services`
- `apps/*` 中的正式承载代码

如果无法沉淀为稳定能力，只能保留为探索记录，不直接视为完成。

---

## 八、README 规范

每个 Demo 的 `README.md` 至少包含以下内容：

```md
# demo-{name}

## 目标

一句话说明该 Demo 解决什么问题。

## 为什么需要这个 Demo

说明该问题的不确定性来源。

## 输入

- 需求背景
- 约束条件
- 参考资料

## 核心方案

说明关键设计决策。

## 验证方式

说明如何运行、如何观察、如何判断通过。

## 验证结果

说明最终结果和结论。

## 已知限制

说明边界条件和不适用场景。

## 沉淀建议

说明应沉淀到哪个 package / app / page。

## 踩坑记录

说明过程中遇到的关键问题。
```

## 九、与 docs 的协作关系

`docs/*` 负责定义和记录，`demo/*` 负责验证和沉淀。

建议协作方式如下：

### 1. `docs/superpowers/specs/*`

职责：

- 定义需求和方案
- 在设计阶段增加 `Demo 判定` 小节

建议新增一张判断表：

| 项目 | 是否可预期 | 是否需要 Demo | 说明 |
|------|------------|---------------|------|
| xxx | 是/否 | 是/否 | 原因 |

### 2. `docs/superpowers/plans/*`

职责：

- 记录正式实现路径
- 对需要 Demo 的事项，先写 Demo 任务，再写正式沉淀任务

### 3. `docs/*` 通用分析文档

职责：

- 记录方法论、复盘、资产演进策略
- 作为团队级决策背景材料

简而言之：

- `spec` 决定做什么
- `plan` 决定怎么做
- `demo README` 记录验证结果是什么

---

## 十、与 packages 的协作关系

`packages/*` 是正式共享资产层。

协作规则：

### 1. Demo 不直接等于 package

Demo 可以引用 package，但不应把 Demo 本身当成一个正式共享包。

### 2. Demo 通过后，才允许沉淀到 package

推荐流程：

1. 在 `demo/*` 中验证
2. 得出稳定模式
3. 将稳定实现提炼到 `packages/*`
4. 在 package 层补类型、导出、测试和文档

### 3. package 只接收“已验证能力”

原则上，不应把明显未验证、边界不清的探索性实现直接沉淀为基础能力。

---

## 十一、与 packages/pages 的协作关系

`packages/pages/*` 更适合作为：

- 场景样板间
- 集成示例页
- 能力展示页

而不是严格意义上的 Demo。

协作规则：

- Demo 先验证单能力
- `packages/pages/*` 再负责组合多个能力
- 页面可用于展示使用方式，但不能替代单能力 Demo

例如：

- `demo-layout-history` 验证历史栈机制
- `demo-drag-canvas` 验证拖拽落点机制
- `packages/pages/src/drag-layout-page.tsx` 负责把这些能力组合为可演示页面

---

## 十二、与 apps 的协作关系

`apps/*` 是正式运行壳，不是 Demo 层。

协作规则：

- Demo 不应默认直接挂到正式 app 路由中
- 只有在确实需要真实容器验证时，才允许通过专门入口临时承载 Demo
- 最终应将通过验证的能力沉淀到 package，再由 app 挂载正式页面或场景

各 app 的主要职责：

- `apps/web`：Web 场景展示、集成验证、产品演示
- `apps/desktop`：桌面端容器适配与正式承载
- `apps/mobile`：移动端容器适配与正式承载

因此，app 层主要验证“集成结果”，不是单能力试验层。

---

## 十三、推荐工作流

当前仓库建议使用以下工作流：

```text
需求 / 想法
  -> 写 spec
  -> 做 Demo 判定
  -> 若需 Demo，则先创建 demo/demo-xxx
  -> 完成验证并写 README
  -> 将稳定方案沉淀到 packages/*
  -> 在 packages/pages/* 或 apps/* 做集成展示
  -> 随产品版本发布
```

这个流程的目标是明确分层：

- Demo 验证能力
- Package 沉淀能力
- App / Page 展示和承载能力

---

## 十四、实施建议

建议先从最小范围试点，不要一次性全面推开。

优先动作：

1. 新增 `demo/README.md` 作为总入口
2. 后续 spec 文档统一增加 `Demo 判定` 小节
3. 选择 1 到 2 个高不确定性能力先做试点
4. 验证流程跑通后，再逐步固化为团队习惯

---

## 十五、结论

本仓库的 Demo 不应再被视为“示例页面”的别名，而应被定义为：

> 高不确定性能力进入正式资产之前的统一验证层。

通过明确目录、状态、命名、准入/退出标准，以及与 `docs / packages / pages / apps` 的协作关系，当前项目可以在保留既有 monorepo 优势的同时，补上 Demo 驱动方法论最关键的部分。

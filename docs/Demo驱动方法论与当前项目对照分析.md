# Demo 驱动方法论与当前项目对照分析

## 背景

本文基于 [Demo驱动的体系化工作方法论.md](/Users/sunny/work2026/fe-base/Demo驱动的体系化工作方法论.md) ，分析当前 `fe-base` 项目是否符合该方法论，并给出一套适合本仓库的最小落地方案。

目标不是机械照搬方法论，而是判断：

- 当前项目已经吸收了哪些思想
- 当前项目和方法论的关键差异在哪里
- 现有方式的优劣是什么
- 如何在不破坏当前 monorepo 工程结构的前提下，引入 Demo 驱动能力

---

## 一、方法论核心摘要

`Demo 驱动的体系化工作方法论` 的核心不是“把工作拆小”，而是：

> 将不确定性隔离在可控范围内验证，再将确定性成果组合进版本。

它强调的不是功能拆分，而是能力拆分；不是为了项目管理，而是为了在人与 AI 协作时控制认知复杂度和结果不确定性。

该方法论有几个关键点：

- 判断标准不是“会不会做”，而是“做完后结果是否可预期”
- 不确定的事先做 Demo，确定的事直接进版本
- Demo 应该是单能力、可独立验证、可复用、可沉淀的认知单位
- Demo 的 README 是跨会话记忆载体，必须沉淀验证结果、限制和踩坑
- 版本的形成方式应是：已有能力直接改动 + 新 Demo 验证通过后的能力集成

## 三、当前项目符合方法论的地方

### 1. 强调能力沉淀，而不是只做单点业务

这一点和方法论高度一致。

根文档明确将项目定义为“前端能力底座”，强调：

- 将通用能力沉淀为共享包
- 通过组合能力支撑不同应用
- 面向多端和多场景复用

这和方法论里“Demo 属于团队能力库，不属于某个功能模块”的理念是同向的。

### 2. 共享包结构天然支持“能力积木化”

`packages/ui`、`packages/hooks`、`packages/store`、`packages/pages` 等结构，本质上已经具备“能力单元”的雏形。

这意味着当前项目并不是功能堆砌，而是有明确的能力边界意识。只不过这些能力单元目前主要体现为正式工程资产，而不是方法论中的“Demo 单元”。

### 3. 已经存在一定的样例验证机制

像 `drag-layout-page`、`table-form-demo-page` 这样的页面，已经承担了以下作用：

- 验证共享组件能否在真实场景下工作
- 让能力可以被看见、被组合、被试用
- 为后续复用提供直观参照

从“用实际运行结果验证能力”这个角度看，它们和 Demo 有相似性。

## 四、当前项目与方法论的关键差异

虽然方向一致，但当前项目并不完全符合 `Demo 驱动` 方法论，主要差异在执行层。

### 1. 当前项目不是“先 Demo 再集成”，而是“先设计/计划再直接进入正式工程”

方法论强调：

- 不确定性先隔离验证
- 验证通过后再组合进版本

当前项目更常见的流程是：

- 写设计文档
- 写实现计划
- 直接在 `packages/*` 或 `apps/*` 中完成实现
- 再通过页面或应用路由观察效果

这意味着“不确定性”并没有被显式隔离，而是较早进入了正式工程。

### 2. 缺少独立的 Demo 载体

方法论中的 Demo 有比较明确的结构：

- `context/`
- `src/` 或 `doc/`
- `README.md`

当前仓库里基本没有独立的 `demo/demo-*` 目录，也缺少面向“单能力隔离验证”的专门工作区。

现有的验证大多发生在：

- 正式共享包代码中
- 页面物料中
- 应用路由中

这更像主工程内验证，而不是隔离验证。

### 3. 样例页更像“场景展示”而不是“单能力 Demo”

例如 [packages/pages/src/drag-layout-page.tsx](/Users/sunny/work2026/fe-base/packages/pages/src/drag-layout-page.tsx) 实际上组合了多种能力：

- 拖拽布局
- 表格组件
- JSON 表单
- 弹窗
- localStorage 持久化
- 撤销/重做

这类页面对产品展示和场景演示很有价值，但从方法论视角看，它更像“集成后的样例页面”，而不是一个严格的单能力 Demo。

方法论更倾向于先拆成：

- `demo-drag-canvas`
- `demo-layout-history`
- `demo-component-registry`

验证清楚后，再组合成页面。

### 4. 当前文档更偏“如何做”，缺少“验证结果与边界”的沉淀

当前项目的设计文档和实现计划写得比较完整，但主要解决的是：

- 要做什么
- 怎么拆任务
- 涉及哪些文件

而方法论要求 Demo README 重点沉淀的是：

- 结果是否验证通过
- 验证数据是什么
- 边界条件是什么
- 已知限制是什么
- 后续如何集成
- 踩过哪些坑

当前仓库在“过程设计”上较强，在“验证结论沉淀”上偏弱。

### 5. 当前流程没有显式区分“可预期改动”和“不可预期探索”

方法论最重要的动作之一是先判断：

> 这件事做完后，结果可预期吗？

当前项目虽然有设计和计划，但没有看到固定的 `Demo 判定` 步骤，因此容易把这些工作混在一起：

- 纯确定性的工程实现
- 新能力探索
- 场景集成验证
- 外部依赖行为验证

这会让“应该直接做”的事情和“应该先 Demo”的事情都走同一条流程。

## 五、当前方式的优劣分析

## 优点

### 1. 工程化程度高

当前方式直接围绕正式仓库资产建设，能力完成后马上进入共享包或应用，避免了“Demo 写完后没人接入”的断层。

### 2. 更适合前端基础设施型 monorepo

这个仓库不是单点功能项目，而是平台型前端底座。很多能力天然需要在真实工程容器中验证，例如：

- 样式体系
- 跨包依赖
- 路由挂载
- 多端兼容
- 打包和类型边界

因此“只在隔离环境验证”不一定足够，主工程中的集成验证本身就是必要的。

### 3. 设计文档和计划链路清晰

当前已有：

- 设计文档
- 实现计划
- 共享资产沉淀
- 路由和页面验证

这说明项目不是无序开发，而是有较清晰的工程节奏。

## 缺点

### 1. 对不确定性的管理不够显式

当前流程没有一个清晰步骤来区分：

- 已知能力内的确定性改动
- 需要隔离验证的新能力或新方案

这样容易导致：

- 把高风险探索直接并入正式代码
- 将“能实现”误认为“结果已验证”

### 2. 样例与正式资产边界不够清晰

当前一些页面既像示例，又像验证场，又像产品物料。这样虽然灵活，但会带来认知混合：

- 哪些页面是能力演示
- 哪些页面是正式可复用资产
- 哪些只是试验性结果

这些边界在方法论里会由 Demo 状态和 README 明确标注。

### 3. 缺少跨会话的“验证记忆”

设计文档记录的是预期方案，实现计划记录的是执行路径，但它们都不完全等价于“结论型记忆”。

方法论中的 README 更偏向：

- 我们验证过什么
- 结果如何
- 限制是什么
- 下次遇到类似问题应该如何复用

当前这部分沉淀不够，AI 或新人跨会话恢复上下文时成本仍然偏高。

### 4. 容易把复杂场景页面误判成单一能力已被验证

一个页面能跑通，不等于其中每个能力边界都验证清楚了。

例如拖拽布局页面能运行，并不 automatically 意味着以下结论都已独立成立：

- 外部拖拽协议稳定
- 撤销/重做模型边界清晰
- 组件注册机制可扩展
- 不同组件尺寸适配策略稳定

方法论要求这些高不确定性点尽量单独验证。

---

## 六、综合判断

当前项目不是“不符合”该方法论，而是“只落了前半段”。

它已经很好地吸收了以下思想：

- 面向能力而不是单功能
- 强调复用与组合
- 强调长期能力积累
- 通过场景页验证共享能力

但还没有完整落下以下动作：

- 在进入正式工程前先隔离不确定性
- 通过独立 Demo 形成能力验证单元
- 用 README 沉淀验证结果和边界条件
- 在流程中显式区分“直接做”和“先 Demo”

因此更准确的描述是：

> 当前项目是“能力沉淀型 monorepo 工程”，而不是“完整的 Demo 驱动工程”。

---

## 七、推荐的最小落地方案

不建议把当前仓库整体改造成“所有工作都先做 Demo”的结构，那会破坏现有工程节奏，也不适合平台型前端仓库。

更适合的做法是：

> 在现有 `monorepo + specs/plans` 体系上，补一层 `demo-driven` 机制，用于承接高不确定性能力。

### 方案原则

- 保留现有 `apps/*`、`packages/*`、`docs/superpowers/*` 主结构
- 仅对高不确定性事项引入 `demo/*`
- Demo 通过后再把稳定方案沉淀到 `packages/*`
- 继续保留设计文档和计划文档，但增加 `是否需要 Demo` 的判定步骤

这是一个“最小侵入”的集成方案。

## 九、建议的流程改造

将当前流程：

`设计文档 -> 实现计划 -> 正式实现 -> 页面验证`

改为：

`设计文档 -> Demo 判定 -> 必要时先做 Demo -> 正式实现/集成 -> 页面验证 -> README 沉淀`

### 1. 在设计文档中增加一节：Demo 判定

每个设计文档都增加一个表格：

| 项目 | 是否可预期 | 原因 | 是否需要 Demo |
|------|------------|------|---------------|
| 已有表单字段扩展 | 是 | 已有实现模式 | 否 |
| 新拖拽协议接入 | 否 | 外部交互边界未验证 | 是 |
| localStorage 持久化 | 是 | 常规实现 | 否 |
| 多端共享拖拽能力 | 否 | 移动端适配路径不确定 | 是 |

判定标准统一为：

- 团队是否做过
- 做完后结果是否可预期
- 是否依赖外部系统或复杂交互
- 是否有明显集成风险

### 2. 仅对“不确定项”创建 Demo

以下情况建议优先进入 `demo/`：

- 新交互协议
- 新三方库接入
- 多端兼容策略
- 配置驱动边界问题
- 渲染或拖拽类复杂行为
- 性能优化是否有效

以下情况建议直接做：

- 常规 CRUD
- 已验证组件扩展
- 样式调整
- 已有模式下的字段增加
- 明确可预期的类型与接口改动

### 3. Demo 通过后再沉淀到 packages

推荐工作顺序：

1. 在 `demo/demo-xxx` 中验证能力
2. 在 `README.md` 中沉淀结论
3. 将稳定代码或模式提炼到 `packages/*`
4. 在 `packages/pages/*` 或 `apps/*` 中做场景组合验证

这样可以区分：

- Demo：验证能力边界
- Packages：沉淀正式资产
- Pages/Apps：组合成场景

## 十、当前项目中“Demo”和“页面样例”的边界建议

建议将现有仓库里的载体角色区分清楚：

### 1. Demo

定位：

- 用于隔离验证不确定性
- 单能力
- 独立可运行或独立可观察
- 必须有 README 记录结论

### 2. Packages

定位：

- 正式共享资产
- 稳定能力沉淀区
- 供多个应用复用

### 3. Pages

定位：

- 组合式场景样例
- 用于能力展示、集成验证、使用示范

### 4. Apps

定位：

- 承载真实路由、应用容器、多端接入

这四者不要混成一个概念。

---

## 十一、建议先落地的三个最小动作

为了避免改造过重，建议先做以下三个动作，而不是一次性全面推行。

### 动作一：新增 `demo/` 根目录和 README 模板

目标：

- 给高不确定性能力一个明确归属
- 建立统一结构

至少要有：

- 目录命名规范
- README 模板
- 状态约定：`active / superseded / archived`

### 动作二：给后续设计文档补上 `Demo 判定` 小节

目标：

- 强制区分“直接做”和“先 Demo”

这一步改动最小，但收益很高，因为它会改变团队的判断习惯。

### 动作三：挑一个高不确定性能力试点

不要从所有能力开始，先挑一个最适合的方法论试点，例如：

- 拖拽协议抽象
- 多端组件注册机制
- JSON Form 配置边界验证
- Desktop/Mobile 复用策略验证

试点完成后再决定是否扩大范围。

---

## 十二、该方案的预期收益

如果按上述方式落地，项目会得到以下收益：

- 更清楚地识别哪些事值得直接做，哪些事必须先验证
- 避免把高不确定性探索过早并入正式工程
- 让 AI 和新人都能通过 Demo README 快速恢复上下文
- 让 `packages/*` 中沉淀的能力更接近“已验证能力”，而不是“尚在试验中的能力”
- 让页面样例的角色更清晰，不再承担过多“实验场”职责

---

## 十三、该方案的代价与注意点

这套方案也有成本，需要明确约束。

### 1. 不要把所有工作都 Demo 化

Demo 只服务“不确定性管理”，不是所有事情都要绕一圈 Demo。

### 2. 不要把集成页当作 Demo 的替代

场景页可以验证集成效果，但不能替代单能力验证。

### 3. 不要让 Demo 直接耦合正式工程内部实现

Demo 应尽量独立，避免共享隐式依赖，否则会失去隔离意义。

### 4. README 不是可选项

没有 README 的 Demo，等于没有形成团队资产。

---

## 十四、结论

当前 `fe-base` 项目与 `Demo 驱动的体系化工作方法论` 并不冲突，甚至在“能力沉淀”和“组合式架构”上高度一致。

真正的差别在于：

- 当前项目更偏“工程资产沉淀”
- 方法论更偏“AI 协作下的不确定性隔离与验证沉淀”

因此，最合理的方向不是推翻现有结构，而是在现有 `monorepo + specs/plans` 流程上补上 `demo-driven` 这一层。

一句话总结：

> 当前项目已经具备“能力库”的骨架，下一步要补的是“对不确定性做独立 Demo 验证，并把验证结果沉淀为可复用记忆”。

# Demo 判定模板

本模板用于补充到 `docs/superpowers/specs/*` 设计文档中，帮助在设计阶段明确：

- 哪些事项可以直接做
- 哪些事项需要先做 Demo
- 为什么需要做 Demo

使用原则：

- 每个 spec 建议都包含这一节
- 判定标准统一使用“结果是否可预期”，而不是“会不会做”
- 如果某项明显属于高不确定性能力，应先进入 `demo/*` 验证，再进入正式实现

---

## 可直接复制的小节模板

```md
## Demo 判定

本次需求先按“做完后结果是否可预期”进行判断。

| 项目 | 是否可预期 | 是否需要 Demo | 原因 | 计划去向 |
|------|------------|---------------|------|----------|
| xxx | 是/否 | 是/否 | 说明原因 | 直接进 packages / 先做 demo |
| xxx | 是/否 | 是/否 | 说明原因 | 直接进 apps / 先做 demo |

### 判定结论

- 直接做：
  - xxx
  - xxx
- 先做 Demo：
  - `demo-xxx`
  - `demo-xxx`

### 说明

- “直接做”表示该项结果高度可预期，可直接进入正式工程实现。
- “先做 Demo”表示该项存在明显不确定性，应先在 `demo/*` 中隔离验证。
```

---

## 判定标准

设计阶段建议逐项检查以下问题：

### 1. 团队做过吗

- 做过多次，且路径稳定：通常不需要 Demo
- 没做过或只做过类似但未完全验证：倾向需要 Demo

### 2. 结果可预期吗

- 写完后结果高度确定：通常不需要 Demo
- 写完后仍需通过实际运行、交互或跨端验证才能确认：倾向需要 Demo

### 3. 是否依赖外部系统或复杂行为

- 若依赖三方库真实行为、浏览器交互、容器行为、多端差异：倾向需要 Demo

### 4. 是否存在明显集成风险

- 单点改动、边界清晰：通常不需要 Demo
- 涉及多个模块、多个 package、多个端：倾向需要 Demo

---

## 建议的判断表述

为了避免写成空泛描述，建议采用以下表述方式：

### 推荐写法

- `可预期：已有组件扩展模式，结果边界清晰`
- `需要 Demo：react-grid-layout 的外部拖拽落点行为未验证`
- `需要 Demo：Desktop 与 Web 对设计令牌映射策略尚未验证`
- `可预期：仅为已有表单 schema 增加字段，不涉及新机制`

### 不推荐写法

- `感觉可以直接做`
- `问题不大`
- `先做再看`
- `理论上应该可行`

---

## 与计划文档的协作方式

如果某项在 spec 中被判定为“需要 Demo”，则在对应 plan 中应体现为两段工作：

### 1. Demo 验证任务

- 创建 `demo/demo-xxx`
- 完成最小验证实现
- 写 README 记录结论

### 2. 正式沉淀任务

- 将通过验证的模式抽取到 `packages/*`
- 在 `packages/pages/*` 或 `apps/*` 中做集成展示

也就是说：

- spec 负责判定需不需要 Demo
- plan 负责拆出 Demo 任务和正式沉淀任务

## 示例

```md
## Demo 判定

本次拖拽编排能力设计按“做完后结果是否可预期”进行判断。

| 项目 | 是否可预期 | 是否需要 Demo | 原因 | 计划去向 |
|------|------------|---------------|------|----------|
| 侧边栏列表展示 | 是 | 否 | 常规 UI 展示，边界清晰 | `packages/ui` |
| 外部拖拽到画布 | 否 | 是 | react-grid-layout 外部拖拽行为需要实际验证 | `demo/demo-drag-canvas` |
| 撤销/重做历史栈 | 否 | 是 | 复杂交互下状态边界未验证 | `demo/demo-layout-history` |
| 页面路由接入 | 是 | 否 | 已有 Next.js 路由模式 | `apps/web` |

### 判定结论

- 直接做：
  - 侧边栏列表展示
  - 页面路由接入
- 先做 Demo：
  - `demo-drag-canvas`
  - `demo-layout-history`

### 说明

- UI 展示和路由接入属于可预期工程改动，直接进入正式实现。
- 拖拽落点和历史栈边界具有明显不确定性，应先在 `demo/*` 中验证。
```
